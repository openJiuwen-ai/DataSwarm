# 内容质量约束

渲染器只保证结构与自包含；下面这些是 spec 文案的硬要求。

## 结论先行

- `analysis` 的 `summary` 写 3-5 条，第一条是最重要的结论；管理层 30 秒能读完。
- 每个 section 的 `title` 是结论句（「SP 州贡献过半增量」），不是标签（「州分布分析」）。
- `conclusion` 必须带数字与方向；没有数字的结论视为未完成。

## 数字可追溯

- 关键数字绑定 `evidence_refs` 或 `sql`；报告层派生数字（份额、环比、合计）挂
  其输入成分的全部引用。
- **多行加总 / 折算数字不要手写**：用 `table` 让脚本算，或在 spec 里只写输入值。
  誊写错位不会被渲染器拦截。
- KPI 优先用 `value_column` + `evidence_refs` 从 CSV 取值，不誊写 `value`。
- 数字与单位成对出现；百分比变化写 `pp`（百分点）还是 `%` 要区分。

## 洞察与归因

- 洞察不能复述图表数字，要说明「这意味着什么」。
- 归因结论至少排除一种替代解释（`alternatives` 或 `alternative_checked`）；
  写清「现有维度解释了 X%，剩余 Y% 未找到集中解释」。
- 区分事实、推断、未知：`claim_type` 用 `fact` / `interpretation` / `uncertainty`。
- 不声称已证明因果；说明机制与方向即可。

## 行动建议

- 每条写对象与动作（「对 SP 州追加投放」），不写「加强运营」。
- 必带 `expected_impact`：量化预期 + 估算依据（如「按当前 CAC 与转化率估算」）。
- 没有量化依据时，宁可写「待验证」，不要编数。

## 局限

- `limitations` 写 2-3 条，绑定事实：样本范围、覆盖缺口、未验证项。
- 不写空泛的「数据可能有误差」。

## 语言

- 禁用模糊词：明显、显著、差不多、大幅、较好；改用数字或区间。
- JSON 文案里不要用 ASCII 双引号，内部引号用「」或“”。
- 对比块的差异表必须有「解读」列，回答差异意味着什么。
