# 探索纪律（decision=explore 的首轮探索前先读本文件）

探索的目的是**补物理信息**（表/列/join/取值/基数），不是「看看数据有什么」。
无序探索浪费轮次（预算：required ≤3 轮），按下面的顺序走。

---

## 探索顺序（三段，按序）

### 第一段 · 补 schema 缺口

- 优先从 context 子包取（`packs.schema_tables` 已有的表列不再摸库——
  list_tables/describe 只在 context 没覆盖该表时用，同表不查两次）
- 召回不中目标对象时用 `recall_more` 换问法重召回，**然后才**考虑 describe
- **禁止用算术拼凑近似值**：某列召回不到（如「商品总额」召不回明细表），
  正确动作是 schema 探索找明细表/相关列，**不是**用「支付额 - 运费」这类
  减法推算——推算引入系统性偏差且报告无法察觉

### 第二段 · 基数与分布预判（写 SQL 前）

- 维度基数 × 时间粒度 = 预估行数：**超 500 行截断线的先降粒度**
  （日→周/月）或收窄维度，不要等编译截断后回炉
- 维值候选在 context 的 values 通道里——分组列的取值先确认（写
  `WHERE region IN (...)` 前知道有哪些 region）
- 时间列的粒度先确认（日/周/月），跨粒度对比要先对齐

### 第三段 · 采样验证（有疑点才做）

- 对「这列能不能当过滤条件」「join 键是否对齐」有疑点时，probe_values /
  check_join 确认，一轮做完

---

## 空结果回退矩阵

执行成功但结果为空时，**不要把空当结论**。按序排查后才能认定「无数据」：

1. **回查 scope**：时间范围/过滤条件是否过窄（是不是过滤掉了全部行）
2. **回查歧义**：是不是口径理解错了（查的列对不对）
3. **回查 SQL**：过滤条件/Join 是否把数据筛没了

排查后仍为空 → 结论写「该口径下无数据」，**不是「值为 0」**——
「无数据」和「值为 0」是两个完全不同的业务结论。

---

## 留空不猜

字段口径三来源（召回子包 / 术语库定义 / schema 列注释）都拿不到时：

- **登记 missing，不猜**——用模型先验填充口径是取数错误的隐性来源
- 属于业务口径缺失（如「流水含不含退款」）→ 只能 clarify（2.3① 已定），
  禁止靠探查数据自行认定
- 属于物理信息缺失 → 本文件的探索顺序补
